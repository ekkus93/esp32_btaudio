## 1. Phase result

FD-12 is software-complete for the stable HFP event contract defined in `ESP_BT_AUDIO_FULL_DUPLEX_TODO_2026-07-27.md`.

The command protocol now emits these bounded records:

```text
EVENT|HFP|PROFILE|<state>|<mac>|<session>
EVENT|HFP|AUDIO|<state>|<codec>|<session>
EVENT|HFP|MODE|<old>|<new>|<reason>|<session>
EVENT|HFP|I2S|<state>|<error>|<session>
EVENT|HFP|HEALTH|<severity>|<reason>|<count>|<session>
```

The records are emitted through the existing command-interface `EVENT` path, so they retain the established rule that events are broadcast to every configured command UART rather than routed only to the UART that issued the last command.

## 2. Event ownership and architecture

The event contract is implemented under `components/bt_manager`:

- `components/bt_manager/include/bt_hfp_event_contract.h`
- `components/bt_manager/bt_hfp_event_contract.c`

The authoritative duplex-state transition functions decide whether an event is meaningful. The formatter does not poll state and does not infer transitions after the fact.

This keeps event emission attached to the same locked state changes that already enforce:

- active peer identity;
- session generation;
- legal profile/audio/I2S transitions;
- fault and quarantine rules;
- explicit recovery.

Command code does not call ESP HFP APIs, and the event formatter does not bypass the manager/state layer.

## 3. Stable wire values

FD-12 uses dedicated compact wire mappings. It does not transmit raw C enum integers or internal enum identifier strings.

Examples:

- `BT_HFP_PROFILE_SLC_CONNECTED` -> `SLC_CONNECTED`
- `BT_HFP_AUDIO_CONNECTED_CVSD` -> `CONNECTED_CVSD`
- `BT_HFP_CODEC_CVSD` -> `CVSD`
- `BT_DUPLEX_MODE_A2DP_PLUS_HFP_MIC` -> `A2DP_MIC`
- `BT_HFP_I2S_QUARANTINED` -> `QUARANTINED`
- `BT_AUDIO_HEALTH_FAULTED` -> `FAULTED`

Stable mode-reason tokens are:

```text
COMMAND
SESSION_BEGIN
RECOVERY
POLICY
```

Stable health-reason tokens are derived from the explicit `esp_err_t` class, including:

```text
RECOVERED
NO_MEMORY
INVALID_ARGUMENT
INVALID_STATE
INVALID_SIZE
NOT_FOUND
NOT_SUPPORTED
TIMEOUT
OPERATION_FAILED
STATE_CHANGE
UNKNOWN_ERROR
```

Stable I2S error fields use names such as `ESP_OK`, `ESP_ERR_TIMEOUT`, `ESP_ERR_INVALID_STATE`, `ESP_FAIL`, and `ESP_ERR_UNKNOWN`.

## 4. Field validation and sanitization

The formatter accepts only bounded stable tokens generated by internal mapping functions.

Peer addresses are validated as exact 17-character Bluetooth MAC addresses, canonicalized to uppercase, and rejected if they contain protocol delimiters, control characters, malformed separators, or non-hexadecimal characters.

A global profile lifecycle event that occurs before a peer session exists uses:

```text
<mac> = NONE
<session> = 0
```

Generation-bound AUDIO and I2S events reject session zero.

I2S fault or quarantine events require a non-OK error. Non-fault I2S events require `ESP_OK`. Inconsistent records are rejected rather than normalized into plausible output.

Health diagnostic text remains in the authoritative status snapshot but is not inserted into the event record. This prevents arbitrary diagnostic text from becoming a protocol-field injection surface.

## 5. Meaningful transitions and duplicate suppression

PROFILE, AUDIO, MODE, and I2S events are emitted only when the corresponding authoritative state value changes.

Calling a state setter repeatedly with the same value does not produce duplicate records.

Examples:

- repeated `CONNECTING` profile callbacks produce one PROFILE transition event;
- repeated HFP audio `CONNECTING` updates produce one AUDIO event;
- setting the requested mode to its current value produces no MODE event;
- repeated I2S `STARTING` synchronization produces one I2S event.

AUDIO events are formatted after the authoritative transition derives the codec, so a confirmed CVSD transition emits `CONNECTED_CVSD|CVSD`, not a stale or independently queried codec.

## 6. No per-frame or per-counter event flood

The following high-frequency operations do not emit an event:

- accepted incoming PCM frame accounting;
- dropped incoming PCM frame accounting;
- I2S underflow counter increments;
- I2S timeout counter increments;
- callback timing/counter updates.

This prevents one event per PCM callback or ring operation.

Those conditions remain visible through `HFP STATS`. HEALTH events are reserved for explicit severity transitions or recovery, not raw counter movement.

## 7. Health threshold contract

A HEALTH event is emitted only when the authoritative health severity changes.

Updating `last_error` or diagnostic text while the severity remains unchanged updates the snapshot but does not emit a duplicate HEALTH event.

Every emitted HEALTH transition receives a monotonic process-lifetime count. The count is not a PCM-frame count and is not reset by `HFP RESETSTATS`.

Explicit recovery emits:

```text
EVENT|HFP|HEALTH|OK|RECOVERED|<count>|<new-session>
```

when the previous health was not OK.

## 8. Event-delivery failure visibility

The shared command response path previously ignored:

- an uninstalled configured UART driver;
- negative `uart_write_bytes()` results;
- short UART writes.

FD-12 makes those outcomes explicit.

For an event broadcast, every configured port is attempted. If one port succeeds and another fails, the surviving port still receives the record, but the API returns the first delivery failure instead of reporting complete success.

The authoritative duplex state records an HFP event-delivery failure as:

- health degraded from OK to DEGRADED when applicable;
- exact delivery error in `last_error`;
- `HFP event delivery failed` in `last_error_text`.

The state transition that triggered the event is not rolled back merely because its diagnostic record could not be delivered. Rolling back authoritative Bluetooth state would create a false state model.

The delivery-failure recorder does not recursively emit another HEALTH event. A failed UART cannot trigger an infinite event-failure loop.

A stale delivery failure from an older generation cannot degrade a newer session.

## 9. Immediate delivery policy

FD-12 uses immediate bounded UART delivery through the existing command path.

It does not add:

- an unbounded event queue;
- automatic retries;
- replay after reboot;
- fake delivery success;
- silent record truncation.

If delivery fails, the current state snapshot exposes that failure. Recovery/retry policy may be added later only with an explicit bounded design.

## 10. I2S error compatibility boundary

FD-12 adds `bt_duplex_set_i2s_state_with_error()` for callers that have a specific fault cause.

The existing compatibility setter, `bt_duplex_set_i2s_state()`, remains available. For a fault or quarantine transition where the legacy caller supplies no specific cause, it emits the explicit generic token `ESP_FAIL`; it never emits `ESP_OK` for a fault.

This is visible loss of diagnostic precision, not silent success. Future I2S/audio-control call-site refinement can pass the exact local error through the error-aware API without changing the FD-12 wire format.

## 13. Explicit boundaries and residual risk

Software validation does not prove:

- physical UART0/UART2 electrical delivery;
- behavior when a real UART cable or downstream receiver disappears mid-record;
- byte-level record ordering under simultaneous callbacks from multiple runtime tasks;
- real HFP profile, SLC, SCO/eSCO, codec, or I2S event timing;
- real earbud event sequences;
- physical GPIO32/33/27 I2S output;
- coexistence with I2S1 RX, UARTAUDIO streaming, A2DP playback, or long-duration soak.

FD-12 does not queue or retry failed events. The failure is made visible in authoritative status instead.

The compatibility I2S state setter reports `ESP_FAIL` when a faulting legacy caller has not supplied a more specific cause. This is explicit but less precise than the error-aware API.

The health-event count and event-delivery diagnostic state are RAM-resident and reset on reboot or full duplex-state deinitialization. `HFP RESETSTATS` does not reset them.
